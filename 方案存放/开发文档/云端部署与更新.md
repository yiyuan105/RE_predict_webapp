# 云端部署与更新（Docker）

本文是**部署与更新的唯一来源**：镜像构建、容器编排、端口与环境变量、数据/模型卷挂载、首次部署、日常更新、回滚、健康检查与故障排查全部写在这里。
运维侧的其余内容（数据更新、匹配逻辑、对外内容维护、公告发布流程、接口字段范围）见 [维修手册](../维修手册.md)，维修手册不再重复部署步骤。

- 适用范围：`v1.1.2` 起的 RE_predict_webapp（Django + gunicorn，完全容器化）
- 服务器要求：Linux（amd64）、Docker 24+、Docker Compose v2（`docker compose`）、可出网（构建依赖与 Open-Meteo 取数）
- 本文允许出现内部路径、镜像名与命令；这些内容不会通过前端页面或对外接口暴露给访客

---

## 1. 交付物

| 文件 | 作用 |
|------|------|
| `Dockerfile` | 镜像定义：Python 3.13-slim、安装依赖、收集静态文件、gunicorn 启动 |
| `docker-compose.yml` | 单服务编排：端口、环境变量、卷挂载、健康检查、重启策略 |
| `.env.example` | 环境变量模板，复制为 `.env` 后填真实值（`.env` 不入库、不进镜像） |
| `.dockerignore` | 构建上下文排除项（`.git`、`方案存放/`、`.env` 等） |
| `models/` | 随机森林模型、中国边界、气候/土壤分区（已在仓库内，也可改为卷挂载） |
| `RE_predict_webapp/announcements.json` | 公告数据；挂载到容器后可在线改，无需重建镜像 |

`Dockerfile` 现状（与仓库一致）：

```dockerfile
FROM docker.1ms.run/library/python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN python manage.py collectstatic --noinput
ENV DJANGO_DEBUG=false
CMD ["gunicorn", "mysite.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "2", "--timeout", "120"]
```

- 基础镜像走 `docker.1ms.run` 镜像源，国内构建更稳；外网环境可换成 `python:3.13-slim`。
- `collectstatic` 在构建阶段执行，静态文件由 WhiteNoise 直接在进程内提供，不额外起 Nginx 静态目录。
- `--timeout 120` 覆盖首次预测（加载地理数据与模型 + 气象请求）的耗时；反代超时需同步调大。

## 2. 镜像构建

在仓库根目录（`Dockerfile` 所在目录）执行：

```bash
# 版本号与发布版本一致，便于回滚
docker build -t re-predict-webapp:1.1.2 .
```

Windows 本地构建（PowerShell）：

```powershell
cd "D:\编程\ICT_Re_predict\mysite"
docker build -t re-predict-webapp:1.1.2 .
```

要点：

- 构建上下文包含 `models/`（约 250 MB），镜像体积较大属正常；`docker images` 可见约 1 GB 以内。
- 依赖里的 `geopandas` / `pyogrio` / `pyproj` / `shapely` 官方 wheel 已自带 GDAL、PROJ、GEOS，**无需额外安装系统库**。
- 修改依赖（`requirements.txt`）后必须重新构建，容器里不会自动安装。
- 建议每次发布保留旧 tag，不要 `docker image prune` 掉上一个版本，回滚靠它。

## 3. 容器编排

`docker-compose.yml`（仓库根目录，可直接使用）：

```yaml
services:
  re-predict:
    build:
      context: .
      dockerfile: Dockerfile
    image: re-predict-webapp:1.1.2
    container_name: re-predict
    restart: unless-stopped
    ports:
      - "127.0.0.1:8000:8000"
    env_file:
      - .env
    environment:
      DJANGO_DEBUG: "false"
      MODEL_DATA_DIR: /app/models
    volumes:
      - ./models:/app/models:ro
      - ./RE_predict_webapp/announcements.json:/app/RE_predict_webapp/announcements.json:ro
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/api/announcements/', timeout=5)"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
```

- **端口**：容器内 gunicorn 监听 `8000`；宿主机只绑 `127.0.0.1:8000`，公网入口交给反向代理。需要临时直连时改成 `"8000:8000"`，验证完再收回。
- **环境变量**：`.env` 注入（见第 4 节），compose 里再兜底 `DJANGO_DEBUG=false`。
- **数据卷**：`./models` 以只读方式覆盖容器内 `/app/models`，模型或地理数据更新时只替换宿主机文件并重启容器即可，不必重建镜像。
  注意：**宿主机目录为空会遮挡镜像自带的数据**（预测会报 `DATA_UNAVAILABLE` / `MODEL_UNAVAILABLE`），全新环境先确认 `models/` 完整。
- **公告卷**：把 `announcements.json` 单文件挂进容器，服务端发布公告时改宿主机文件即可，接口每次请求重新读取，**无需重启**。
- **健康检查**：打 `/api/announcements/`（只读、纯本地、不访问 Open-Meteo、不加载模型），适合做存活探针；不要用 `/api/predict/` 做探针，它会触发外部请求与模型加载。
- **重启策略**：`unless-stopped`，服务器重启或进程异常退出后自动拉起。

## 4. 环境变量

| 变量 | 必填 | 示例 | 说明 |
|------|------|------|------|
| `DJANGO_DEBUG` | 是 | `false` | 线上必须 `false`；`true` 会暴露调试页 |
| `DJANGO_SECRET_KEY` | 是 | 随机长字符串 | 生成：`python -c "import secrets; print(secrets.token_urlsafe(50))"`；**不要复用示例值** |
| `DJANGO_ALLOWED_HOSTS` | 是 | `ecofluxforecast.cn,www.ecofluxforecast.cn,8.133.180.65,127.0.0.1` | 逗号分隔；缺域名会返回 400 |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | 建议 | `https://ecofluxforecast.cn,https://www.ecofluxforecast.cn` | 走 https 域名时必须填，否则表单/后台 CSRF 校验失败 |
| `MODEL_DATA_DIR` | 否 | `/app/models` | 数据目录；compose 已固定为容器内路径 |
| `RF_MODEL_CACHE_SIZE` | 否 | `4` | 同时缓存的随机森林模型数（每个约 20 MB），内存紧张时降到 `2` |
| `WEATHER_ENDPOINT` | 否 | `https://api.open-meteo.com/v1/forecast` | 气象数据源；历史回算可用 `https://historical-forecast-api.open-meteo.com/v1/forecast` |
| `WEATHER_MODEL` | 否 | 留空 | 留空为 `best_match`；**注意 GFS 不提供土壤湿度**，会导致 `WEATHER_UNAVAILABLE` |
| `WEATHER_TIMEOUT_SECONDS` | 否 | `20` | 气象请求超时，网络差时调大 |
| `WEATHER_FORECAST_DAYS` | 否 | `1` | 取几天预报做当日均值 |

准备 `.env`：

```bash
cp .env.example .env
vi .env      # 至少改 DJANGO_SECRET_KEY / DJANGO_ALLOWED_HOSTS / DJANGO_CSRF_TRUSTED_ORIGINS
chmod 600 .env
```

`.env` 已在 `.gitignore` 与 `.dockerignore` 中排除，不会进仓库、不会被打进镜像。

## 5. 首次部署

### 5.1 服务器准备

```bash
docker --version            # 24+
docker compose version      # v2
```

未装 Docker 时按发行版官方文档安装，并确认当前用户有 docker 权限。

### 5.2 取代码与数据

```bash
mkdir -p /www/wwwroot && cd /www/wwwroot
git clone <仓库地址> mysite
cd mysite
ls models/rf_models | head     # 应能看到 <站点>_rf.joblib
```

模型文件较大，首次克隆较慢；若仓库不含模型，用 `scp`/`rsync` 把 `models/` 补齐后再启动。

### 5.3 配环境变量

见第 4 节（`cp .env.example .env` 后填真实值）。

### 5.4 构建并启动

```bash
docker compose build
docker compose up -d
docker compose ps              # STATUS 应为 healthy（start_period 40s 内为 starting）
docker compose logs -f --tail=100
```

### 5.5 反向代理与域名

容器只监听本机 8000，由 Nginx（或宝塔「网站 → 反向代理」）转发：

```nginx
server {
    listen 80;
    server_name ecofluxforecast.cn www.ecofluxforecast.cn;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 180s;   # 首次预测可能 5~10s，留足余量
    }
}
```

- 上 HTTPS（宝塔「SSL → Let's Encrypt」或 `certbot`），并把 `DJANGO_CSRF_TRUSTED_ORIGINS` 写成 `https://` 形式；
- `proxy_read_timeout` 应大于 gunicorn `--timeout`，否则长预测会被反代先断开（表现为 504）。

### 5.6 上线冒烟检查

```bash
# 只读接口：200 + JSON
curl -fsS http://127.0.0.1:8000/api/announcements/ | head -c 200
curl -fsS http://127.0.0.1:8000/api/stations/ | head -c 200
curl -fsS http://127.0.0.1:8000/api/sources/ | head -c 200

# 真实预测：应返回 200 与预测值（首次较慢属正常）
curl -fsS "http://127.0.0.1:8000/api/predict/?lat=36.8294&lon=116.5682"

# 境外坐标：应返回 422 OUT_OF_CHINA
curl -s -o /dev/null -w '%{http_code}\n' "http://127.0.0.1:8000/api/predict/?lat=35.68&lon=139.69"

# 页面：应返回 200
for p in / /stations/ /sources/; do curl -s -o /dev/null -w "$p %{http_code}\n" "http://127.0.0.1:8000$p"; done
```

再用浏览器打开域名，确认三页样式与脚本正常、首页能出预测值、公告边栏有内容。

## 6. 日常更新

发布前先在仓库里改版本号：`docker-compose.yml` 的 `image:` tag 与本文命令里的版本保持一致（例如 `1.1.2` → `1.1.3`）。

### 6.1 代码更新

```bash
cd /www/wwwroot/mysite
git pull
docker compose build                      # 按当前 Dockerfile 重建
docker compose up -d                      # 镜像变化后自动重建容器
docker compose ps && docker compose logs --tail=100
```

若只改了 `docker-compose.yml`（端口、环境变量、卷），`up -d` 会重建容器，无需 `build`。

### 6.2 公告更新（无需重启）

```bash
vi /www/wwwroot/mysite/RE_predict_webapp/announcements.json
curl -fsS http://127.0.0.1:8000/api/announcements/ | head -c 300   # 立即生效
```

条目格式与下架方式见 [维修手册 · 对外展示内容维护](../维修手册.md#6-对外展示内容维护)。

### 6.3 模型 / 地理数据更新

```bash
tar czf ~/backup/models-$(date +%F).tar.gz models/          # 先备份
# 覆盖 models/rf_models/<站点>_rf.joblib、models/Chinageo/、models/atoshp/、models/soilshp/
docker compose restart re-predict                            # 进程内单例缓存，必须重启才生效
```

### 6.4 训练情况与站点配置更新

`config.json`（站点清单、`training` 训练结果、特征顺序）在镜像内。改完二选一：

```bash
# 方式 A：重建镜像（推荐，版本可追溯）
git pull && docker compose build && docker compose up -d

# 方式 B：单文件挂载，改完重启即可（在 docker-compose.yml 增加一卷）
#   - ./RE_predict_webapp/config.json:/app/RE_predict_webapp/config.json:ro
```

### 6.5 离线部署 / 镜像搬运（内网服务器）

沿用既有做法：在外网机器构建并导出，服务器上导入。

```bash
# 构建机
docker build -t re-predict-webapp:1.1.2 .
docker save -o re-predict-v112.tar re-predict-webapp:1.1.2
scp re-predict-v112.tar user@server:/www/wwwroot/

# 服务器
docker load -i /www/wwwroot/re-predict-v112.tar
docker compose up -d          # compose 的 image 指向同一 tag
docker image ls | grep re-predict-webapp     # 确认新 tag 已导入
```

## 7. 回滚

**代码 / 镜像回滚**（保留旧 tag 的前提下）：

```bash
docker image ls | grep re-predict-webapp          # 确认旧版本还在
# 把 docker-compose.yml 的 image 改回旧 tag，例如 re-predict-webapp:1.1.1
docker compose up -d
docker compose ps && docker compose logs --tail=50
```

也可以直接 `git checkout <上一个发布 tag>` 后 `docker compose build && up -d`，两种方式都要重新做一次第 5.6 节的冒烟检查。

**数据回滚**：

```bash
docker compose down
tar xzf ~/backup/models-2026-11-20.tar.gz -C /www/wwwroot/mysite
docker compose up -d
```

**公告回滚**：`announcements.json` 走 git 或单独备份，改回后立即生效，无需重启。

回到稳定版本后，若确认新版本彻底废弃，再清理镜像：`docker image rm re-predict-webapp:<废弃 tag>`。

## 8. 健康检查与监控

```bash
docker compose ps                      # STATUS=healthy 表示探针通过
docker inspect --format '{{json .State.Health}}' re-predict | python -m json.tool
docker compose logs --tail=200 re-predict       # 业务日志（stdout）
docker stats re-predict --no-stream             # CPU / 内存
```

- 业务日志由 `settings.LOGGING` 输出到 stdout：预测完成、气象失败、未预期异常都会记录，用 `docker compose logs` 查。
- 建议在宿主机加一条定时检查（crontab 每 5 分钟）：

```bash
*/5 * * * * curl -fsS -o /dev/null http://127.0.0.1:8000/api/announcements/ || echo "$(date) re-predict 不健康" >> /var/log/re-predict-check.log
```

- 容器重启策略已设为 `unless-stopped`，异常退出会自动拉起；若反复重启，先看日志再决定是否回滚。

## 9. 故障排查

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `docker compose up` 后容器反复重启 | 启动即异常（依赖缺失、端口占用） | `docker compose logs --tail=200`；`ss -lntp \| grep 8000` 查端口 |
| 访问域名 502 / 504 | 反代后端未就绪、或预测超过反代超时 | 先 `curl 127.0.0.1:8000`；调大 `proxy_read_timeout` 与 gunicorn `--timeout` |
| 页面能开但无样式、无交互 | 静态文件没收集 / 被卷遮挡 | 确认镜像构建阶段跑过 `collectstatic`；不要在 `/app/staticfiles` 挂空目录 |
| 访问返回 400 Bad Request | `DJANGO_ALLOWED_HOSTS` 不含当前域名 | 补域名或服务器 IP 后 `docker compose up -d` |
| 表单提交或后台 403 CSRF | `DJANGO_CSRF_TRUSTED_ORIGINS` 未填 | 补 `https://` 域名后重建容器 |
| 预测提示「未能获取 Open-Meteo 气象数据」 | 容器出网受限 / 超时 / 气象源不提供土壤湿度 | 检查容器网络；调大 `WEATHER_TIMEOUT_SECONDS`；`WEATHER_MODEL` 置空或换源 |
| 预测提示「气象数据缺失」 | 用了 GFS 等不提供土壤水分的模型 | `WEATHER_MODEL` 置空，或用默认 `best_match` |
| 预测提示「该站点的模型暂不可用」 | `models/rf_models/<站点>_rf.joblib` 缺失或损坏 | 补齐模型文件；确认卷挂载不是空目录；`docker compose restart` |
| 提示「地理或站点数据暂时无法加载」 | 边界/分区数据缺失、`config.json` 格式错 | 看日志里的 detail；检查 `models/` 与挂载 |
| 首次预测特别慢（数秒～十几秒） | 首次加载地理数据与模型 | 正常；上线后打一次预热请求 |
| 内存占用高 / 被 OOM Kill | 模型缓存过大、worker 过多 | 降 `RF_MODEL_CACHE_SIZE`；在 Dockerfile/命令里把 `--workers` 调成 1 |
| 公告边栏显示「暂无公告」 | 挂载路径错、JSON 格式错、条目都 `active:false` | `curl /api/announcements/` 看返回；单文件挂载时宿主机文件必须存在 |
| 训练情况页面数值与预期不符 | `config.json` 的 `training` 未更新 | 改配置后重建镜像（或挂载该文件）并 `up -d` |

## 10. 安全清单

- `.env` 权限 `600`，不入库、不进镜像；`DJANGO_SECRET_KEY` 每个环境独立，示例值不可直接用。
- `DJANGO_DEBUG=false`；不要为排查方便长期开 `true`（会暴露堆栈与配置）。
- 8000 只绑 `127.0.0.1`，公网只开 80/443，HTTPS 终结在反向代理。
- 服务器防火墙只放行 80/443/SSH；Docker 端口映射不要写成 `0.0.0.0:8000`。
- 不把 `db.sqlite3`、备份 tar、`.env` 提交到仓库（`.gitignore` 已覆盖）。
- 发布前自查：`docker compose exec re-predict python manage.py check --deploy`。
